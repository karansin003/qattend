Data Security & Architecture Guide

Encrypted. Isolated. Transparent.

A technical overview of how QAttend protects student credentials, enforces multi-user isolation, and handles data retention and deletion.

1. Core Security Architecture

QAttend is engineered specifically for university students, with privacy and security principles embedded directly into its system architecture. We operate on the principle of least privilege and strict data isolation.

Architectural Security Highlights

  • Zero Credential Sharing: Your credentials are never shared with or accessible to third parties, other students, or public pages.
  • AES-256-GCM Encryption: Passwords stored for background re-authentication are encrypted using authenticated cryptography.
  • Firebase Authentication: Industry-standard user identity handling and password management powered by Google Firebase.
  • Strict Multi-Tenant Isolation: Every student account has isolated database entries, session files, and notification states.

2. Firebase Authentication & User Identity

To avoid vulnerabilities associated with self-managed password storage, QAttend integrates directly with Google Firebase Authentication:

  • Credential Protection: When you register or change your QAttend password, the credentials are processed and stored securely by Firebase Authentication.
  • Token Verification: The QAttend application server receives cryptographically signed identity tokens (JWTs) and verifies them against official Google public certificates.
  • No Plaintext Passwords: QAttend never writes student account passwords to application logs, persistent disk files, or unencrypted database columns.

3. QUMS Credential Encryption (AES-256-GCM)

To provide continuous attendance tracking, daily 8:30 AM schedules, and 7:00 PM assignment reminders, QAttend must occasionally re-establish an authenticated session with the university portal when previous session cookies expire.

To do this safely without exposing student passwords:

  • Authenticated Encryption: Passwords are encrypted using AES-256-GCM (Advanced Encryption Standard in Galois/Counter Mode), which provides both confidentiality and tamper detection.
  • Key Derivation via Scrypt: A 256-bit cryptographic key is derived using the memory-hard scrypt key derivation function combined with an isolated salt and an environment secret (ENCRYPTION_KEY).
  • Unique Initialization Vector (IV): A fresh, cryptographically random 12-byte initialization vector is generated for every encryption operation. No two stored records share the same ciphertext representation.
  • 16-Byte Authentication Tag: Every encrypted payload includes a 16-byte GCM authentication tag. If any byte of the ciphertext is altered, decryption immediately fails rather than returning corrupted or vulnerable data.

4. Multi-Tenant Session & Storage Isolation

Each user's environment in QAttend is completely partitioned:

  • Session File Protection: QUMS session files are stored under data/qums-sessions/<userId>.json. These files are saved with strict 0600 permissions (read and write access granted exclusively to the operating system process owner).
  • Database Row Isolation: In the database, attendance tracking state (known_attendance), assignment records (known_assignments), and Telegram links are scoped strictly by foreign key to your specific user ID.
  • Telegram Channel Boundary: Exactly one Telegram chat ID maps to one student. When notifications are pushed, the message builder addresses you by your real student name retrieved from QUMS—never your email address.

5. Web Application Hardening

The web dashboard and API endpoints incorporate multiple layers of defensive engineering:

  • Secure HTTP Cookies: Browser session cookies are configured with httpOnly: true (preventing client-side JavaScript access and XSS theft), sameSite: 'lax' (protecting against Cross-Site Request Forgery), and secure: true in production environments (ensuring cookies are transmitted only over encrypted HTTPS).
  • Rate Limiting: Sensitive authentication routes—including login, registration, password reset, and token verification—are protected by dedicated in-memory rate limiters to block brute-force password guessing and resource abuse.
  • Private Route Exclusion: Private dashboards (/dashboard), setup pages (/qums-setup, /telegram-setup), administration portals (/admin), and API endpoints (/api/) are protected by mandatory session middleware and are strictly disallowed from public indexing in robots.txt.

6. User Control & Data Deletion Practices

You maintain full sovereignty over your information at all times:

Reset QUMS Connection

The Reset / Delete QUMS Connection button on the setup screen immediately and permanently purges your saved credentials and active session files from the server.

Disconnect Telegram

Clicking Disconnect instantly unlinks your Telegram chat ID. No further automated alerts or summaries can be sent to your chat.

Full Account Deletion

You can request complete deletion of your account, authentication links, and all stored data by contacting us via the Contact page.
