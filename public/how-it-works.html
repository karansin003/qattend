How QAttend Works

Connect. Monitor. Automate.

An open, transparent look under the hood: from initial setup to headless browser relays, state deduplication, and automated background workers.

1. The Four-Stage Connection Lifecycle

QAttend is designed to be set up once. After initial configuration, the system monitors your academic records on the server 24/7 without requiring you to keep a browser tab open or repeatedly log into the university portal.

1

User Registration

You create an account with your email. Authentication, token verification, and password resets are handled via Google Firebase Authentication.

2

Headless QUMS Link

You provide your QID and university password once. A headless browser session relays the official visual CAPTCHA for you to solve.

3

Telegram Deep Linking

A single click generates a secure Telegram deep link. Pressing "Start" permanently pairs your specific Telegram chat ID with your QAttend account.

4

Continuous Monitoring

Background workers track daily timetables, live lecture marks, retroactively entered attendance, and assignment deadlines automatically.

2. The Headless Browser Relay Explained

Universities protect student portals with dynamic security tokens and visual CAPTCHA challenges. QAttend bridges this securely using Playwright Chromium running in headless mode:

  • Initialization: When you enter your credentials on the setup screen, the backend spins up an isolated Chromium context that navigates directly to the university's official portal.
  • Visual Relay: The portal's CAPTCHA element is screenshotted and streamed as a base64 image directly to your browser. QAttend never uses automated OCR or third-party cracking services; you solve the CAPTCHA personally.
  • Session Extraction: Once authenticated, the browser extracts the necessary session cookies and writes them to an isolated, user-specific JSON file (mode 0600). The browser process is then cleanly terminated to preserve server resources.
  • Encrypted Reconnection: Your university password is encrypted with AES-256-GCM using a unique initialization vector. If your portal session expires, you do not need to retype your password—clicking "Reconnect" auto-fills your credentials, requiring only the fresh CAPTCHA code.

3. Background Worker Architecture

QAttend runs several specialized background scheduler and watcher loops, each dedicated to a distinct academic monitoring responsibility:

Monitoring Loop Schedule / Interval Data Source Purpose & Action
Morning Scheduler Every morning at 8:30 AM IST Timetable API Extracts today's lectures, matches room numbers and faculty, and pushes the morning schedule.
Live Attendance Watcher Every 5 minutes (08:30–17:00 IST) Daily Periods API Detects when lectures transition from Not Marked to Present or Absent; alerts user instantly.
Month Register Scanner Every 10 minutes Month Register API Identifies retroactively updated records for past dates and notifies user with the real lecture date.
Assignment Scanner Every 30 minutes Student Assignment API Identifies new teacher-published assignments and alerts user with topic details and deadlines.
Deadline Reminder Every evening at 7:00 PM IST Known Assignments DB Warns students if an assignment deadline expires today so work is submitted in time.

4. Deduplication & False-Positive Elimination

A common failure of automated scrapers is alert duplication—bombarding users with repeated notifications whenever a script restarts. QAttend implements strict idempotency contracts:

  • State Marked Before Send: When an event is detected, its composite key (combining user ID, course code, period, and status) is recorded in PostgreSQL or persistent JSON storage before dispatching to Telegram, with automatic rollback if transmission fails.
  • Zero Duplicate Alerts on Boot: On application deployment or server reboot, historical records are seeded silently as baseline state without triggering duplicate alert storms.
  • Cross-Loop Filtering: Marks detected by the 5-minute fast loop during daytime hours are automatically deduplicated against the 10-minute month loop, guaranteeing single delivery.

5. Safe Session Lifecycle & Reconnection

If the university server restarts, cookies may expire. QAttend handles this gracefully:

  1. If an authenticated request returns a session rejection, QAttend flags the user status as expired.
  2. An immediate alert arrives in your Telegram chat with a direct 🔐 Reconnect QUMS button.
  3. Clicking reconnect opens the QUMS setup screen with your QID and decrypted password already populated.
  4. You solve the fresh CAPTCHA, and active tracking resumes instantaneously.
